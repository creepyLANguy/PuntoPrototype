## API compatibility policy

The public JSON API is version `v1` by contract even though the current public URLs are unversioned. Existing `/a`, `/r`, `/s` and `/m` paths are treated as the v1 compatibility surface.

**Compatibility rules:**

- Additive response fields are backwards compatible.
- Existing field meaning, types, enum values and nullability must not change without a migration notice.
- Removing or renaming a field, changing an enum, or changing scoring semantics is a breaking change.
- New API versions must use an explicit path/version rather than silently changing v1 semantics.
- Deprecated fields must remain for at least one documented deprecation period and be listed in the changelog.

## Common HTTP contract

Public JSON endpoints support `GET` and `OPTIONS`; other methods return `405`.

Success responses are JSON with `success: true`. Current error responses are `{ "success": false, "error": "..." }`. The production-hardening target is the structured error contract in [`public-api.md`](public-api.md), including stable `code`, human-readable `message`, and optional `requestId`.

Public responses use `Access-Control-Allow-Origin: *`. They contain only data intended for public live-score consumption and require no browser authentication.

`fetchedAt` is the timestamp at which the payload was generated by the function. It is **not** a guarantee that the request reached Firestore at that instant; CDN/function caches can return a previously generated payload.

`revision` is an opaque equality token. Consumers must compare it for equality/inequality and must not sort it or assume it is monotonically increasing.

## Rate limiting and polling

The current API does not advertise a hard per-client rate limit. Until one exists, clients must use the recommended polling pattern:

1. Poll `/r/{courtId}` every ~2 seconds for interactive displays.
2. Fetch `/a/{courtId}` only when `revision` changes.
3. Fetch `/s/{courtId}` only at game/set boundaries or on demand.
4. Fetch `/m/{courtId}` only when momentum data is displayed or refreshed.

A future rate limit must return `429` with the structured error format and, where practical, `Retry-After`.

## Security boundary

Public score endpoints are intentionally unauthenticated. `postEvent` is a device-control endpoint and is a different trust boundary. The current implementation authenticates a device only by `deviceId`; this is insufficient as a production security model if an attacker can discover or replay a device identifier.

**P0 hardening requirements:**

- Authenticate devices with a per-device secret or equivalent cryptographic credential; do not treat a public NFC/tag value as sufficient authentication.
- Add request freshness/replay protection and a unique event identifier.
- Make scoring-event ingestion idempotent.
- Authorize REGISTER/SPECTATE transitions server-side.
- Never log secrets, credentials or complete device provisioning payloads.
- Apply rate limiting/abuse protection to device ingestion.

The detailed target protocol is in [`device-protocol.md`](device-protocol.md).

## Contract testing

The OpenAPI document is the canonical machine-readable HTTP contract. CI should validate that public endpoint responses and errors conform to it. Scoring fixtures should additionally verify every scoring-mode combination and replay/idempotency scenario.

## Change management

API changes must update, in the same pull request:

1. `docs/api/openapi.yaml`.
2. The relevant human-readable API document.
3. Examples/fixtures and contract tests.
4. `docs/api/CHANGELOG.md`.
5. Version/deprecation notes for any breaking change.

See [`api/README.md`](api/README.md) for the contribution checklist.
